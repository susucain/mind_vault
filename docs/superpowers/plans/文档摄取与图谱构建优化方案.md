## 一、需求原文与目标

### 1.1 第一轮需求（摄取与图谱的资源/性能）

1. **重试机制效率低下**：发生错误后重试会触发完全从头开始的重建，已成功构建的 chunk 被重复处理，浪费 token 与时间。
2. **图谱构建性能问题**：图谱构建耗时过长，影响整体处理效率与体验。
3. **资源消耗控制**：图谱构建耗时且 token 消耗大，需要用户可控——
   - 上传流程中提供「是否进行图谱构建」的明确选项；
   - 默认**不**构建图谱；
   - 仅当用户明确选择时才触发图谱构建；
   - 未选择时只做向量索引，跳过图谱构建。

### 1.2 第二轮需求（全链路系统性优化）

对文档上传完整流程（上传 → 解析 → 索引 → 图谱）做系统性优化，并建立可量化的评估口径：

1. **上传**：提升稳定性与速度；支持 PDF / Word / TXT 等多种格式的批量上传。
2. **解析**：优化内容解析算法，提升文本提取准确率；处理特殊格式（表格、图片中的文字）。
3. **索引**：改进索引构建策略，优化索引结构与更新机制，提升检索效率。
4. **图谱质量**：增强实体识别与关系抽取，提高图谱准确性与完整性。
5. **评估**：建立性能评估指标（上传成功率、解析准确率、索引构建时间、图谱构建质量等），并做测试验证，确保效率、准确性、稳定性均有可证明的提升。

### 1.3 目标与不变量

**优化目标**：资源浪费清零（重试不重复付费）、图谱可关可开且默认为关、图谱耗时显著下降、四链路各有可量化指标与回归手段。

**范围裁剪（2026-10-08 已确认）**：需求中的「图片中的文字（OCR）」不在本次范围——当前没有视觉模型与 OCR 配额，改为「准确识别扫描件 + 明确提示」（§7.3）。其余四项（批量上传与稳定性、解析准确率、索引结构、图谱质量）全量交付；OCR 的重启前置条件已留档。

**不变量（本方案不得破坏）**：
- `ownerId` 强隔离：所有查询/写入必须带 owner，跨用户不复用任何数据。
- 摄取阶段协议与 SSE 事件语义不变（`stage/result/done/error`；文档进度走 `stage`）。
- Langfuse 埋点红线：trace 在编排层创建、步骤名用 `runName` 区分、敏感信息脱敏。
- 迁移文件必须在 `app.module.ts` 注册白名单内才会执行。
- `reindex` 保持「全量重建」语义（`documentVersion+1` + 清 ES/Neo4j）；断点续跑只属于 `retry`。

## 二、现状核对（已验证到行号）

### 2.1 当前流水线拓扑

```
上传（API 进程）
  document-upload.service.upload()                     ← 建 job(UPLOADED) + 建 kh_document(Processing)
     └─ publishIndex('document.index')  →  exchange mind-vault.ingestion

摄取（worker 进程 · 队列 mind-vault.ingestion.worker · prefetch(1)）
  document-ingestion.worker.process()
     parsing → 写回 Mongo content/sections
     chunking（1600 字/块，160 字重叠，chunkId = sha256(…+text)）
     embedding（batch 10、批间隔 1000ms）
     indexing（reindex 时先清 ES + Neo4j；然后 indexChunks）
     graphTasks.enqueue(chunks)  ← 无条件入队，每 chunk 一行 kh_document_graph_task（含全文）
     job → READY、kh_document.status → Available

图谱（worker 进程 · 队列 mind-vault.graph.worker · prefetch(GRAPH_WORKER_CONCURRENCY=3)）
  document-graph.worker.process()   ← 与我们说的「并行」指这里：ES 索引完成后图谱任务并行扇出
     GraphExtractionService.extract()（fast 模型，每 chunk 一次 LLM 调用）
     KnowledgeGraphService.indexChunk()（Neo4j 写）
```

关键事实：
- 图谱任务「入队即算完成」——[document-ingestion.worker.ts#L381-L382](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/ingestion/document-ingestion.worker.ts#L381-L382)：先 `enqueue` 再置 `READY`。因此 `READY` / 「已可问答」**不代表图谱已建完**，图谱进度是独立通道（`stage: 'graph'`）。
- 两个 worker 是两个独立队列、独立并发度，互不阻塞。

## 三、问题一：重试会从头重跑，重复消耗 token

### 3.1 根因（三处叠加）

1. **`retry()` 只是把同一个 job 重新投递**——[document-upload.service.ts#L198-L241](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/document-upload.service.ts#L198-L241) 把 `status` 改回 `UPLOADED`（删除类操作改回 `DELETING`），再次 `publishIndex`，`documentVersion` 不变。
2. **`process()` 没有阶段检查点**——[L272-L382](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/ingestion/document-ingestion.worker.ts#L272-L382) 无条件从 parsing 一路跑到 indexing：
   - 重新从 RustFS 下载 / 从 Mongo 取 `sourceBytes`（[L287-L299](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/ingestion/document-ingestion.worker.ts#L287-L299)）；
   - 重新解析并写回 Mongo（[L301-L318](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/ingestion/document-ingestion.worker.ts#L301-L318)）；
   - 重新分块、**重新调用 embedding API 计算全部向量**（[L320-L347](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/ingestion/document-ingestion.worker.ts#L320-L347)）。按 `EMBEDDING_BATCH_SIZE=10`、`EMBEDDING_REQUEST_INTERVAL_MS=1000`（[embedding.service.ts#L16-L32](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/embedding/embedding.service.ts#L16-L32)、[L58-L67](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/embedding/embedding.service.ts#L58-L67)），500 个 chunk 至少要 50 次批调用、约 50s 的硬性间隔；
   - **重新为自己知已成功的 chunk 入队图谱任务**（[L381](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/ingestion/document-ingestion.worker.ts#L381)）→ 每 chunk 再花一次 LLM 调用，这才是「已成功构建的 chunk 被重复处理」的直接来源。
3. **图谱任务表没有去重/复用**——`enqueue()` 每次 `tasks.save(chunks.map(...))`（[L30-L56](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/graph/document-graph-task.service.ts#L30-L56)），同 `chunkId` 会插入新行；`process()` 只对 `READY/CANCELLED` 短路（[document-graph.worker.ts#L131-L138](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/graph/document-graph.worker.ts#L131-L138)），而新行是 `PENDING`，于是必然重新抽取。

另外：`chunkId` 是 `sha256(ownerId:documentId:documentVersion:sectionId:chunkOrder:text)`（[document-chunking.service.ts#L33-L44](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/chunking/document-chunking.service.ts#L33-L44)）——同版本下**文本不变则 chunkId 稳定**，这是做「续跑」的前提；而 `reindex` 会把 `documentVersion+1`（[document-lifecycle.service.ts#L107](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/document-lifecycle.service.ts#L107)）并主动清空 ES/Neo4j（[L363-L372](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/ingestion/document-ingestion.worker.ts#L363-L372)），属于**有意的全量重建**，本次不改其语义。

### 3.2 改法

**核心：把「retry（断点续跑）」与「reindex（全量重建）」的语义分开，并引入 chunk 级检查点。**

现状：`kh_document_chunk` 表不存在，chunk 与向量只活在内存与 ES 里，进程一挂就丢，这是「只能重跑」的根本原因。

**推荐方案 A：新增 `kh_document_chunk` 检查点表**

| 列 | 用途 |
| --- | --- |
| `document_id` + `document_version` + `section_id` + `chunk_order`（唯一键） | 版本内定位；键不用 chunkId，避免解析结果轻微漂移导致全部失配 |
| `chunk_id` | 与 ES 文档 `_id` 对齐 |
| `text` / `parent_context` / `title_path` / `locator_json` | 续跑时直接重建 `DocumentChunk[]`，**无需重新下载与解析原文** |
| `embedding` | 向量检查点（`bytea` 存 float32，1024 维 ≈ 4KB/块；备选 `jsonb`，实现更简单但体积约 3–5 倍） |
| `created_at` | 排障 |

配套改造：
1. `process()` 增加**版本级短路**：若 `(ownerId, documentId, documentVersion)` 已存在完整检查点（行数 > 0 且全部 `embedding` 非空）→ 跳过 parsing / chunking / embedding 三个阶段，直接进入 indexing。job 的 `currentStage` 会从 `indexing` 起跳，进度对前端仍然连续（`updateJob` 已是幂等写）。
2. `process()` 的 `stage` 变量已经记录了失败阶段（[L246](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/ingestion/document-ingestion.worker.ts#L246)、[L399](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/ingestion/document-ingestion.worker.ts#L399)），可直接作为「从哪续跑」的判据（例如 `stage === 'indexing'` 时连解析都不必做）。
3. `enqueue(chunks)` 改为**跳过已完成**：先按 `(ownerId, documentId, documentVersion)` 查 `kh_document_graph_task`，把 `READY` 的 `chunk_id` 集合排除后再建行；同时修复重复行（同 chunkId 已有 `PENDING/PROCESSING` 行时不重复入队）。
4. 图谱任务行不再存 `text` 全文（[document-graph-task.entity.ts#L39-L40](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/graph/entities/document-graph-task.entity.ts#L39-L40)）：worker 处理时按 `chunkId` 从 `kh_document_chunk` 取文本。收益：Postgres 写入量与行膨胀显著下降（每 chunk 少写一份全文），并让「只补建图谱」不再依赖重新解析。

**备选方案 B（不新增表）**：把 ES 当检查点——新增一个按 `(ownerId, documentId, documentVersion)` 回读 `_source`（含 `embedding`、`text`、`titlePath`、`locator`）的查询方法，retry 时用它重建 chunks，只对缺失的 chunk 调 embedding。
- 好处：零新表、零迁移。
- 代价：① `_source` 中 `dense_vector` 每次回读都要传输整个向量数组，500 块要分页多次（单次 `size ≤ 100`）；② 强依赖「解析结果逐字节稳定」——一旦第二次解析文本有差异，`chunkId` 全变，缓存全失配（PDF 元数据、解析库版本都可能造成）；③ reindex 会清空 ES，检查点随之消失。
- 结论：B 能治「图谱重复抽取」，但治不干净「重复 embedding」。**建议 A**（决策点 D1）。

### 3.3 不改的部分

- `reindex`（`documentVersion+1` + 清 ES/Neo4j）保持全量重建语义——分块策略或 embedding 模型变化后必须重建，缓存复用反而会留下脏数据。
- `retry` 仍复用同一个 job 行（[L214-L220](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/document-upload.service.ts#L214-L220)），只是不再重复干活。

**与其他章节的接口**：`kh_document_chunk` 检查点同时是第 5 章（图谱补建）、第 9 章（实体归一与去重）以及第十一章迁移的基础。语义边界：**幂等键（第 6 章）管「同一文件被重复提交」，`retry` 管「同一文档失败重跑」**，两者不重叠——前者防重复建文档，后者防重复付费。

## 四、问题二：图谱构建耗时过长

### 4.1 根因（按影响排序）

| 序 | 根因 | 定位 | 说明 |
| --- | --- | --- | --- |
| 1 | **Neo4j 写入是逐条串行往返** | [knowledge-graph.service.ts#L74-L110](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/graph/knowledge-graph.service.ts#L74-L110) | 每个 chunk：1 次骨架 + 每实体 1 次 + 每关系 1 次。按上限 30 实体 / 50 关系算，单 chunk 最多 **~81 次串行 `session.run`**。取 2–4ms/次，单 chunk 仅往返就 160–320ms；图谱并发度 3 时，500 块的文档要多花 ~30–55s |

### 4.2 改法

**P0（确定性收益，风险低）**
1. **Neo4j 批量写**：`indexChunk` 由「1 + E + R」次串行改为
   - 1 次 `UNWIND` 批量 `MERGE` 实体 + `MERGE (entity)-[:MENTIONED_IN]->(chunk)`；
   - 按关系类型分组（全仓共 8 种，[graph-types.ts](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/graph/graph-types.ts)），每种 1 次 `UNWIND` 批量 `MERGE` 关系，最多 8 次；
   - 合计 **≤10 次**往返（原最多 ~81 次），且与实体/关系数量解耦。
   - 注：关系类型当前是拼进 Cypher 的（[L496-L510](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/graph/knowledge-graph.service.ts#L496-L510)），批量时按类型分组即可，仍走白名单校验，不引入注入面。
2. **入队去重**（与 §3.2 第 3 条同一处改动）：不重复入队已 `READY` / 已在途的 chunk。
3. **跳过低价值 chunk**：新增可配置阈值 `GRAPH_MIN_CHUNK_CHARS`（默认 80），短于阈值的块不入图；同时对规范化后的 `text` 做内容指纹去重（同文档内完全相同的块只抽一次）。
4. **收敛输出上限**：实体 30 → **15**、关系 50 → **30**，并在 `invokeJson` 调用上限制 `max_tokens`（具体数值决策点 D3）。这会降低图谱密度，属于产品取舍。
5. **去掉任务表的 `text` 列依赖**（同 §3.2 第 4 条），改为按 chunkId 取文本。

**P1（可调优）**
6. `GRAPH_WORKER_CONCURRENCY` 默认 3 → **5–8**（需与模型服务配额匹配），并把 `INGESTION_WORKER_ENABLED` / `GRAPH_WORKER_CONCURRENCY` 这两个直接读环境变量的项收进 [configuration.ts](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/config/configuration.ts)（现在是 `config.get('GRAPH_WORKER_CONCURRENCY', 3)` 直读 env，与项目其他配置读取方式不一致）。
7. **可观测埋点**：每 chunk 已在日志里输出 `elapsedMs`（[L187](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/graph/document-graph.worker.ts#L187)），补充拆分「extract 耗时 / Neo4j 耗时」，并在文档级聚合输出一行汇总（chunk 数、总耗时、平均、LLM 调用次数）。以此作为改造前后对比的基线（验收 §14.4）。

**明确不做**：把多 chunk 合并成一次 LLM 调用（batch 抽取）。理由：会改变抽取口径（跨块实体消歧、上下文串味），且失败粒度变粗导致重试成本更高；在 P0 已能取得主要收益的前提下不值得引入这个变量。若 P0 后仍不达标，再单独立项评估。

**关联**：本章只解决图谱的**耗时与成本**；图谱的**准确性/完整性**（实体识别、关系抽取质量）在第 9 章单列，两者的改动面几乎不重叠（本章动写入与调度，第 9 章动 prompt 与归一化）。

## 五、问题三：用户可控的图谱构建（默认关闭）

### 5.1 设计

- **开关落在文档上**：`kh_document.graph_enabled boolean NOT NULL DEFAULT false`。理由：是否建图谱是文档级属性（可事后补建），而 job 是一次性的（[document-ingestion-job.entity.ts](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/entities/document-ingestion-job.entity.ts)），retry/reindex 都会新建或复用 job，不适合承载这个语义。

### 6.2 改动清单

**P0 — 稳定性（先修「会丢掉工作」的两条）**

- **U2 幂等键**（治 F2）：上传接口支持 `Idempotency-Key` 头；`kh_document` 增 `upload_key`，唯一索引 `(owner_id, upload_key)`。同 key 重复提交 → 返回**既有** `documentId`/`jobId`（不重复建文档、不重复投递）。
  - 前端：`QueuedUpload.localId` 直接作为幂等键（[id()](file:///Users/susucain/开发/mind-vault/mind_vault_web/src/hooks/use-upload-queue.ts#L16-L18) 已生成 uuid），重试时沿用同一个 `localId`。
  - **边界如实说明**：HTTP 无法「先查后传」，所以幂等键省掉的是**服务端重复建文档与重复索引**，不是重复传输的字节（要多传一次文件才能发现重复）。这是本项的价值边界，不做夸大。
- **U7 投递可靠性**（治 F1）：`failStaleJobs()` 增加分支——对 `status = Uploaded` 且**从未有过心跳**的 job（即大概率从未被消费），先按 `publishRetryCount < N` **重投一次**，仅当重投也失败或超次数才判 `Failed`。同时 `upload()` 中 `publishIndex` 失败不再让整个请求 500（记录错误日志、保留 job，交给重投或用户重试）。
  - **明确不做 outbox 表**：当前 RabbitMQ 为单节点、无镜像队列，引入 outbox + 中继进程的复杂度与收益不匹配；上面的「有界重投」已覆盖「消息丢/投递失败」这一主要场景。

**P1 — 成本与资源**

- **U3 内容指纹 → 重复即拒**（治 F3；决策 D13 = **拒绝**）：`kh_document` 增 `content_hash`（sha256，**服务端**对 buffer 计算）。同 `ownerId` + 同 `datasetId` 已存在同 hash 且未删除 → **拒绝并返回 409**，响应体带 `duplicateOf: { id, name, createdAt }`，前端提示「该文件已存在」并高亮既有文档。
  - **不提供 `force` 覆盖路径**（按 D13）：确需重新入库时先删除原文档。这样避免「误点仍然上传」造成的无意重复付费。
  - 拦截发生在**接收完文件、建文档之前**（hash 需完整字节才能算），所以省下的是 embedding / 图谱抽取 / 存储，**不是传输字节**。
  - 为什么服务端算 hash：前端算 hash 需要把 100MB 文件完整读一遍（`crypto.subtle` 全量摘要），既不能省下传输，又多一次主线程/Worker 开销——本项目标是**避免重复付费**，不是省流量。
  - **秒传（chunk 级复用）本次不做**：现有 chunk 通过 `documentId` 归属并参与 `datasetIds`/`ownerId` 过滤，复用意味着把「文档→chunk」改成多对多，会同时冲击检索过滤、删除清理与图谱归属，改动面远超收益。列为后续独立评估。
- **U4 流式落盘**（治 F4）：`FileInterceptor` 由内存改为 `diskStorage`（临时目录）或对象存储启用时直传；`upload()` 内部签名由 `buffer` 改为「临时路径 + size」，Mongo `sourceBytes` 镜像仅在 ≤8MiB 时保留（现状逻辑不变）。原文只服务**首次解析**，与 §3 的检查点方案 A 互补（A 让 retry 不再需要原文）。
- **U6 并发双闸门**（治 F4）：现状按「文件个数」限流 3；改为 `maxConcurrentFiles=3` **且** `maxConcurrentBytes=150MB`，超出字节闸门时大文件自动串行排队。

**P1 — 进度、取消与体验**

- **U5 进度走 SSE**（治 F6）：Web 端改订阅 `GET /documents/events`（服务端已实现，含心跳与阶段事件）；轮询仅作为 SSE 不可用/断线期间的兜底对账（`documents/:id/status` 单次调用）。
  - `EventSource` 不能携带 `Authorization` 头，因此复用既有 `use-sse.ts` 的 **fetch + ReadableStream** 手写解析路径（与问答流同一套做法），不为文档单开鉴权通道。
  - 小程序无 `EventSource`，仍走轮询——端侧差异在 §6.3 明示。
- **U8 取消语义**（治 F5）：两档实现，按你选择：
  - 档 1（推荐，成本低）：`uploading` 阶段 abort 并调 `POST /documents/:id/cancel` 将 job 置 `CANCELLED`；`processing` 阶段**按钮置灰并标注「已进入处理，无法取消」**（当前 worker 无中途取消检查点，硬砍需在 stage 循环里加检查）。
  - 档 2（完整）：worker 在各 stage 之间检查 `job.status === CANCELLED` 并中止，图谱任务同步置 `CANCELLED`。
- **U9 字节级上传进度**（治 F7）：`fetch` 没有上传进度事件，需把 `uploadDocument` 改用 `XMLHttpRequest`（`upload.onprogress`）以驱动 `progress`，与阶段百分比拼接展示（上传 0–100% → 处理阶段接管）。

**P2 — 校验加固**

- **U1 魔数复核**（治 F8）：`%PDF-`、`PK\x03\x04`（docx/xlsx/pptx）、`\xD0\xCF\x11\xE0\xA1\xB1\x1A\xE1`（老 Office 复合文档）、文本类（可 UTF-8 解码且无 NUL 字节）。不匹配 → 400 + 明确 `code`（`FILE_TYPE_MISMATCH`）。
- **U10 支持格式动态清单**：新增 `GET /documents/supported-formats`，前端与小程序**不再各自硬编码**白名单（现状前端 [ALLOWED_EXTENSIONS](file:///Users/susucain/开发/mind-vault/mind_vault_web/src/hooks/use-upload-queue.ts#L8-L10)、小程序 `library.ts`、后端 [SUPPORTED_EXTENSIONS](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/document-upload.service.ts#L30-L42) 三处重复），并让 §7.6 的 `soffice` 探测结果自动反映为「老格式不可用」。

1. **资产 key 全局重名 → 跨文档互相覆盖**：图片名是 `pdf_img_p{页}_{序号}.{ext}`，**不含 documentId/ownerId**（[pdf.parser.ts#L84](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/parser/parsers/pdf.parser.ts#L84)），而上传统一挂在 `pdf-images/` 前缀下（[file-parser.service.ts#L193-L204](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/parser/file-parser.service.ts#L193-L204)）。两份不同 PDF 的第 1 页第 1 张图同名 → **后上传覆盖先上传**，先入库的文档引用到别人的图。

**生产环境将切换到阿里云 OSS**（`RustfsService` 已预留 OSS 分支，见 §7.2 `A1`），因此 key 规则与权限校验必须**存储无关**，不能在本地/NAS 路径上打补丁。

> **排期决定（已确认 2026-10-08）**：A1 **按阶段排期执行，不单独紧急修**（所属阶段见第 13 章）。OCR 本次不立项，A1 的对象量级不变，但仍需在 OSS 切换前完成。

## 八、索引链路：结构与更新机制

> 本节针对第二轮需求第 3 条。现状事实见 §2.5。

### 8.0 为什么「改 mapping 不生效」是首要问题

`ensureIndex()` 只判断「索引存在就 return」（[elasticsearch-index.service.ts#L53-L57](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/retrieval/es/elasticsearch-index.service.ts#L53-L57)），物理索引名硬编码 `mind_vault_chunks_v1`（[L45](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/retrieval/es/elasticsearch-index.service.ts#L45)）。后果：**任何 mapping 变更（新增字段、换 analyzer、改 embedding 维度）在已有环境上都不会生效**，只能人工删索引重建。

因此本章所有「索引结构优化」都建立在 **8.1 别名 + 版本化索引** 之上——没有它，后续改动上线后"看不出变化"。附带一点：`dims` 由 `EMBEDDING_DIMENSION`（默认 1024）在建索引时固化（[L84-L89](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/retrieval/es/elasticsearch-index.service.ts#L84-L89)、[L281-L289](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/retrieval/es/elasticsearch-index.service.ts#L281-L289)），换 embedding 模型必然重建，别名机制让这件事从"停服"变成"切一刀"。

### 8.1 别名与版本化索引（P0 · `I1`）

- 物理索引 `mind_vault_chunks_v{n}` + 读写别名 `mind_vault_chunks`。
- `ensureIndex()` 改为：别名存在 → 读取后端索引的 `_meta.mappingVersion` 并与**期望指纹**比对；不一致则记录 warn（**不在应用启动时自动建/切**，避免多副本竞争，切换交给显式脚本）。
- 代码改动点收敛为「把 `this.indexName` 换成别名」：写入 [L103](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/retrieval/es/elasticsearch-index.service.ts#L103)、关键字检索 [L205 附近](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/retrieval/es/elasticsearch-index.service.ts#L205)、向量检索、`getByChunkIds` [L237](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/retrieval/es/elasticsearch-index.service.ts#L237)、`deleteByDocument` [L253](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/retrieval/es/elasticsearch-index.service.ts#L253)、`markDocumentDeleted` [L266](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/retrieval/es/elasticsearch-index.service.ts#L266)。

### 8.2 写入策略（P1 · `I2`）

- **refresh 收敛**：`indexChunks` 目前每批 `refresh: 'wait_for'`（[L126-L129](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/retrieval/es/elasticsearch-index.service.ts#L126-L129)）。worker 是**分批**写（[document-ingestion.worker.ts#L336-L352](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/ingestion/document-ingestion.worker.ts#L336-L352)），于是每批都等一次刷新，flush 次数被放大到批数倍。改为 `refresh: false`，由 worker 在**该文档全部批次写完**后显式刷新一次（检索侧只关心"文档级可见"）。
- **失败明细**：`errors: true` 时只抛一个泛化错误（[L130](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/retrieval/es/elasticsearch-index.service.ts#L130)）。改为从 `result.items` 提取失败条目，抛 `BulkIndexError` 携带 `{ chunkId, reason }[]` 并写入 job 失败原因——否则线上只能看到「Elasticsearch bulk 索引失败」，无法定位是 mapping 冲突还是单条超长。

| Recall@10 / MRR | 标注 query 集上的召回与排名 | 验证 I3（分块）与 I5（参数）不劣化检索质量 |
| 检索 P95 延迟 | keyword / vector / hybrid 分别统计 | 验证 I2（refresh 收敛）与别名层无明显开销 |
| 零结果率 | 返回 0 命中的 query 占比 | 语料/分块是否过碎 |
| 高亮可见率 | `highlight != null` 的引用占比 | 验证 I4 的修复效果 |
| `getByChunkIds` 覆盖率 | 返回数 / 请求数 | 验证 I6 |

### 8.7 明确不做

- **不调 HNSW / 量化参数**：当前数据量下不是瓶颈，且需要独立基准环境才能得出可信结论。
- **不按 owner 分索引**：会让别名与重建机制复杂度翻倍，而 `filter` 已能保证隔离。
- **不引入独立向量库（Milvus / pgvector）**：属架构级替换，超出"优化现有链路"的范围。
- **不做检索结果缓存**：在语料频繁更新的阶段，缓存失效成本高于收益。

### 9.1 上下文化抽取（P0 · `G1`）

- 抽取 prompt 注入 **文档标题 + `titlePath` 路径 + 片段序号**（依赖 §7.2 `A7` 的多级 titlePath）；
- 明确禁止指代型与泛化实体名（"本文/该项目/如上所述/该方案"），要求实体名**自足可辨**（必要时补限定语，如"Elasticsearch 倒排索引"而非"它"）；
- 输入范围从 `chunk.text` 扩展为「`parentContext` 摘要 + `chunk.text`」或「前后各 200 字邻居片段」（取舍见 D10）；
- prompt 版本号写入任务记录与日志，使"改了 prompt 质量变好/变坏"可归因（配合 §10 的准确率回归）。

### 9.2 实体归一与别名（P0 · `G2`）

- **规则层（先做，零额外成本）**：NFKC 全半角统一、去括号注释（`（…）`/`(…)`）与尾标点、去首尾引号、英文连字符与下划线统一、保守的单复数归一（只处理明显的尾 `s`，避免误伤中文语境里的英文专名）；
- **展示层**：`Entity` 增加 `aliases`，收集被合并的原始写法，图谱面板可展示「别名：x、y」（前端按现有 `GraphViewNode` 扩展字段）；
- **模型层（可选，见 D11）**：仅对**新出现的实体名**做批量同义判定（一次性喂候选名 + 该 owner 的高频实体名），结果缓存；规则层覆盖不到时才启用；
- **存量合并脚本**：归一规则变化**不会自动合并已有节点** → 需一次性脚本（`MERGE` 目标节点、迁移 `MENTIONED_IN` 与关系边、删除旧节点），并输出「合并前后实体数」对比报告。该脚本可离线执行，属可回滚项（执行前导出受影响子图）。

### 9.3 端点闭合与质量计数（P0 · `G3`）

- 端点解析顺序：① 本 chunk 实体 → ② 同 owner 下按归一名回查 `Entity` → ③ 仍不存在则丢弃；
- **丢弃必须计数并上报**：`droppedRelations` 按原因分类（端点缺失 / 自环 / 类型非法）写入任务结果与日志。这是"提升完整性"最直接的抓手——现状连"丢了多少"都无从得知。
- 同时上报 `truncatedEntities / truncatedRelations`（对应 9.0 的静默截断），使"抽取上限是否过紧"可判断。

### 9.4 confidence 生效（P1 · `G4`）

现状写入即遗忘。三种用法（取舍见 D12）：

| 方式 | 做法 | 代价 |
| --- | --- | --- |
| ① 过滤 | 低于阈值（默认 0.5）的关系不入库 | 激进，可能丢掉真实但表述含糊的关系 |
| ② 标记 + 默认视图过滤（推荐） | 低置信关系仍入库，默认视图隐藏、可开关显示 | 需要在查询与视图两端各加一处过滤 |
| ③ 排序/加权 | 视图按 confidence 排序，边宽/节点大小随置信变化 | 不影响数据完整性，但默认视图仍混杂 |

无论选哪种，都要在**关系查询**（`search` / `neighborhood` / `answerContext`）里体现，并把阈值放进 `graph.*` 配置——现状 `configuration.ts` **没有 graph 段**，30/50/2hops 等全部硬编码。

### 9.5 关系类型与平行边（P1 · `G5`）

- **先度量再动作**：统计 8 类关系的占比与兜底类 `RELATED_TO` 的比例；只有兜底类占比过高，才考虑细分类型（不做无依据的类型扩张）；
- **平行边折叠**：同一对实体的多条同类型边（来自不同 chunk）在**视图层聚合为一条**并标注出现次数/来源片段数；后端**保留多边**（`sourceChunkId` 是"关系归属文档"的依据，删除会破坏文档级过滤与删除清理）；
- 明确 `MENTIONED_WITH` 与 `RELATED_TO` 的边界，否则兜底类会吞噬一切语义。

### 9.6 与第 4 章的分工

本章只动 prompt、归一化、端点解析、过滤与视图聚合；**不动 Neo4j 批量写与调度**（§4）、**不动开关与进度通道**（§5）。两者改动面不重叠，可分别提交。

### 9.7 质量如何度量（口径见第 10 章）

| 指标 | 定义 | 目标方向 |
| --- | --- | --- |
| 端点闭合率 | 1 − `droppedRelations` / 模型给出关系总数 | ↑ |
| 重复实体率 | 同 owner 下"疑似同物"抽样比例（归一前后对比） | ↓ |
| 孤立节点比 | `degree = 0` 的实体占比 | ↓ |
| 类型稳定性 | 同实体 `type` 被覆盖写入的比例 | ↓ |
| confidence 分布 | 关系置信度直方图（用于校验 D12 阈值） | 观测 |
| 抽样 precision | 每文档抽 10 条关系人工核对 | ↑ |

### 9.8 明确不做

- **不做多 chunk 合并抽取**（同 §4 理由，单独立项评估）；
- **不做全量模型消歧**：成本不可控，先用规则层 + 可选批量判定；
- **不做图谱版本快照/时间旅行**；
- **不引入专用图谱抽取模型或微调**：与本次目标量级不匹配。

### 11.3 跨链路的数据关联（易被忽略）

`chunkId` 是**由内容派生的**（`owner+document+version+section+order+text` 哈希），因此 §8.3 的分块变更会**同时影响三处已落库的数据**：

| 受影响数据 | 现状 | 处理 |
| --- | --- | --- |
| Neo4j 的 `Chunk` 节点（`MENTIONED_IN` 的落点） | 重建后旧 `chunkId` 的 Chunk 节点失去对应 ES 文档，成为孤儿 | 阶段 K 内对 `graph_enabled = true` 的文档**重跑图谱抽取**，并清理孤儿 Chunk 节点（保留 Document 与 Entity） |
| `kh_chat_citation.chunk_id`（阶段 C/D 引入） | 旧会话的引用详情按 chunkId 查，重建后查不到 | 前端引用卡片**降级显示**：查不到正文时展示文档名 + `locator`（页码/段落）并标注「片段已更新」；**不回填历史引用**（D9） |
| `kh_document_chunk`（检查点表） | 键含 `section_id + chunk_order`，分块变更后与旧记录不匹配 | 新版本 `document_version+1` 天然隔离；旧版本记录在重建完成后删除 |

> 这条决定了 **阶段 K 必须整体发布**（解析层级 + 分块 + 索引结构 + 图谱重跑 + 引用降级），不能拆开上线，否则会出现"索引与图谱指向不同 chunkId"的中间态。

## 十四、验收标准

> 编号沿用首轮 1–6（§14.4 即第 4 条）；7 条起为第二轮新增。

**首轮（图谱可插拔、重试续跑、图谱性能）**

1. **默认不建图谱**：不勾选上传一份文档 → ES 有 chunk，Neo4j 无该文档的 `Document/Chunk` 节点，`kh_document_graph_task` 无行，Langfuse 无 `graph.extract` trace；`GET /documents/:id/status` 的 `graph` 为 `null`。
2. **显式开启则建图**：勾选上传 → 图谱任务全部 `READY`，Neo4j 关系带 `sourceChunkId`，`status.graph.status === 'READY'`。
3. **重试续跑**：在 indexing 阶段制造失败后 `retry` → embedding 调用次数 0（若已过该阶段）；图谱 LLM 调用次数 = 未完成 chunk 数；`kh_document_graph_task` 不新增重复 `chunk_id` 行。
4. **reindex 语义不变**：仍清空 ES/Neo4j 全量重建，`documentVersion+1`。
5. **图谱性能**：同一份 ≥200 chunk 的文档，记录改造前后——`graph` 阶段总时长与单 chunk 平均耗时、LLM 调用次数（Langfuse）、Neo4j 往返次数降至 ≤10 次/chunk。
6. **门禁全绿**：API `npx jest`、`npx nest build`；涉及前端的阶段另跑 Web 四项门禁。

**第二轮（上传 / 解析 / 索引 / 图谱质量 / 指标）**

7. **上传幂等**：同一 `Idempotency-Key` 提交两次 → 返回**同一** `documentId`，库中仅 1 份文档、1 个 job、embedding 调用 1 次。
8. **投递自愈**：人为让首次 `publish` 失败（或丢弃消息）→ 下一轮 stale 扫描后 job 被重投并成功进入处理，无需用户干预。
9. **重复文件被拒**：上传与既有文档同 hash 的文件 → **409** + `duplicateOf`（含既有文档名与创建时间），前端提示并高亮既有条目；库中**不新增**文档与 job；无 `force` 绕过路径。
10. **内存峰值**：3 份 100MB 文件并发上传，API 进程 RSS 峰值 < 1.2GB（记录改造前基线做对比）。
11. **解析可诊断**：扫描件 PDF → `error_code = PARSE_SUSPECTED_SCANNED`（不再是笼统「解析结果为空」），前端文案为「疑似扫描件，暂不支持文字提取」；无 `soffice` 时 `.doc/.xls/.ppt` 在上传阶段即被拒。
12. **内容覆盖**：含表 PDF 的表格并入**对应页**正文（非文末）；含图 DOCX 的图片可正常展示；PPTX 讲者备注出现在正文。
13. **资产隔离（存储无关）**：用他人文档的 asset key 请求 → 404；两份不同 PDF 的同页同序号图片**不互相覆盖**；新 key 满足 OSS 约束（无中文/空格/非法字符、长度合规），`M7` 搬迁脚本在 OSS 上校验通过。
14. **索引可演进**：修改 mapping 后经 `npm run es:migrate` 生效；切换前后同一 query 集检索结果一致。
15. **检索效率**：引用高亮可见率提升（`highlight != null` 占比）；hybrid 参数可从配置调整且 Recall@10 不劣化。
16. **图谱质量**：样本集上「端点闭合率 / 重复实体率 / 类型稳定性」三项可测量，并给出改造前后对比表（含丢弃计数非零即视为可观测）。
17. **指标可用**：`stage_timings` 落库且能算出各阶段耗时；`scripts/eval/*` 产出报告（`--dry-run` 亦可）。
18. **回归**：§10.4 清单中的既有用例全绿，且新增用例覆盖本轮改动点。

| ES 别名切换失败 | 保留旧索引 N 天；一条命令把别名切回 `v{n}`；重建任务可重投 |
| 重建期间检索命中"正在被清空的索引" | 严格遵守「先写新索引 → 再切别名」，禁止沿用现有 reindex 的"先删后写"做全量重建 |
| 归一化规则变更合并了不该合并的实体 | 执行前导出受影响子图；合并脚本按 owner 分批、可在 Neo4j 内回滚（重新导入导出） |
| 幂等键被误复用导致两次上传被判为同一文件 | key 由前端 per-file uuid 生成；服务端对 key 设 24h 有效窗口，超窗视为新请求 |
| 流式落盘引入临时文件泄漏 | `finally` 清理 + 进程启动时清理残留临时目录 |
| 扫描件无 OCR，用户误以为「文档损坏」 | 明确错误码 `PARSE_SUSPECTED_SCANNED` + 文案「疑似扫描件，暂不支持文字提取」（§7.3）；将来重启 OCR 的前置条件已留档 |
| 切 OSS 后存量对象未搬迁 → 老文档插图 404 | 先跑 §11.1 `M7`（搬迁 + 数量/大小校验），切换后旧存储保留只读一段时间再摘除 |
| OSS 的 key 约束比自建 S3 严（中文/空格/非法字符） | key 改为内容哈希命名（§7.2 `A1`）+ `uploadBytes` 文件名规范化；OSS 私有 bucket 需预建并配好 RAM 权限 |
| 并发双闸门导致大文件排队久等 | 闸门按字节计算；前端显示「排队中」而非「上传中」；阈值可配 |
| 别名/param 化引入检索质量回退 | §10.4 的固定 stub 排序稳定性用例 + 样本集 Recall@10 对比 |

回滚总原则：

- **纯增量迁移**（M1/M2/M4/M5/M6）→ 删列删表即可；
- **M3**（删 `text`）的 `down` 必须能补回空列；
- **图谱开关**（A/B）→ 把 `graph_enabled` 默认值改回 `true`，一键回到"总是建图谱"；
- **结构变更批（K）** → 别名切回 + 用旧版本解析器重跑（旧索引保留期内可回滚）；
- **归一化（M）** → 子图导出恢复；
- **指标（O）** → 纯读侧，无回滚风险。
