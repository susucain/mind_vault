## 一、背景与目标

### 1.1 现状

知识库文档阅读（原文预览）当前链路为：**列表页 → 文档详情 → 查看原文**，预览页由左侧章节目录 + 右侧正文组成，支持从聊天引用卡/检索结果卡携带定位参数深链跳转。

现状的核心特征可以概括为一条「**全文入库 → 全文返回 → 全文渲染**」的链路（证据见第三章 P1）：文档正文在摄取阶段即以完整 Markdown 落库，预览接口一次性返回整篇正文与全部章节，前端一次性渲染所有章节。文档在长文档场景下必然表现为首屏慢、内存占用高、滚动卡顿。

### 1.2 目标

按用户提出的四个方向对文档阅读页做系统性优化：

1. **UI 设计**：建立符合阅读习惯的排版与视觉层次，提升可读性。
2. **交互体验**：补齐目录导航、页面跳转、字号调整等阅读刚需能力。
3. **按需加载**：实现滚动触底自动加载后续内容，减少初始加载时间与内存占用。
4. **响应式**：桌面 / 平板 / 移动多档适配，移动端不再是「目录被隐藏」的残缺形态。

### 1.3 非目标（本期不做）

| 项 | 原因 |
|---|---|
| 文档在线编辑 / 批注 / 高亮划线 | 属另一产品形态，与「阅读优化」无直接关系 |
| 原文 PDF/Office 原样还原（版式、分页、脚注） | 解析产物为 Markdown 文本，原样还原需引入 PDF 渲染器，成本与收益不匹配 |
| 检索 / 图谱能力的改动 | 本次仅优化「阅读」，检索与图谱模块不在范围内 |
| 文档解析器（parser）算法重写 | 解析产物结构（`ParsedSection`）已满足分页需求，本期不改解析算法 |
| 多端（小程序）阅读页 | 现有为 Web 端，另行评估 |

数据模型：

- **文档元数据**（Postgres `kh_document`）：`title / summary / tags / status / wordCount / pageCount / contentId …`，**无正文列**，`contentId` 指向 MongoDB。
- **文档正文**（MongoDB `document_content`）：`content`（整篇 Markdown）、`sections: ParsedSection[]`（全部章节）、`pageCount`、`sourceBytes`（原始字节）、`version`。
- **章节模型** `ParsedSection`：`{ sectionId, heading?, text, order, locator }`（[parsed-document.ts](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/parser/parsed-document.ts#L11-L17)），`locator` 支持 `page / slide / sheet / cellRange / lineStart / lineEnd / jsonPath`。

**章节粒度（决定分页可行性）**：以 PDF 解析器为例，**按页生成章节**——`sectionId = section_0001`、`heading = 第 N 页`、`locator = { page: N }`、`order = index`，并过滤空页（[pdf.parser.ts](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/document/parser/parsers/pdf.parser.ts#L174-L202)）。即 `sections` 数组天然按 `order` 有序，是**可稳定分页**的载体。

## 四、优化方案

### 4.1 UI 设计：阅读排版与视觉层次

目标：从「一段段纯文本」升级为「结构化长文阅读」。

| 项 | 方案 | 说明 |
|---|---|---|
| 阅读栏宽 | 正文列设 `max-width: var(--mv-reading-measure)`（默认 `72ch`，约 720px）并居中 | 控制行长在 60–75 字符的可读区间；宽屏下不再横向拉满 |
| 排版尺度 | 使用流式字号与行距（`--mv-reading-font-size` / `--mv-reading-line-height`） | 正文 1.6–1.8 行距；段间距 `margin-block` 而非 `pre-wrap` 空行 |
| 标题层级 | 章节标题用真实 heading 语义（`h2` 章节、正文内 Markdown 标题降级为 `h3/h4`） | 修复 P11 的语义缺失，同时建立视觉层级 |
| Markdown 渲染 | 复用项目既有 `streamdown`（聊天页已用）渲染静态 Markdown | 修复 P2；需评估渲染成本与体积（见待确认项 2） |
| 图片 | Markdown `![](url)` 渲染为 `<img loading="lazy" decoding="async">` | PDF 抽取的图片当前是裸文本，修复后可见 |
| 目录样式 | 章节树（按 `titlePath`/层级缩进）、当前项高亮、当前项左侧色条 | 提升可扫读性 |
| 视觉分隔 | 章节间用细分隔线 + 章节序号徽标，保持与全站 `--mv-*` token 一致 | 复用既有设计语言 |

### 4.2 交互体验

| 项 | 方案 |
|---|---|
| 目录导航 | 左侧 TOC 支持 **滚动联动高亮**（IntersectionObserver scroll-spy）+ 点击平滑滚动 + `aria-current="location"`；长目录支持**搜索/过滤**与**折叠**（按层级） |
| 页面跳转 | 保留 locator 深链定位与高亮；新增**上一章 / 下一章**、**回到顶部**、**阅读进度条**（顶部细进度条 + 百分比） |
| 字号调整 | 工具条提供 4 档字号（`0.9 / 1 / 1.125 / 1.25 rem`）+ 行距（紧凑/标准/宽松），写入 `localStorage` 持久化，首屏读取避免闪烁 |
| 移动端 | ≤767px 提供**顶部阅读工具条**（返回 / 目录 / 字号 / 进度）与**目录抽屉**（复用 `Drawer`），替代当前直接隐藏目录 |
| 定位反馈 | 深链命中时高亮目标段并短暂显示「已定位到 第 N 页」提示；未命中时给出明确提示而非静默 |
| 加载反馈 | 触底加载显示**骨架屏**（保持已有章节不闪动）；加载失败提供**局部重试**；无更多内容时显示「已到底部」 |

### 4.3 按需加载（核心）

#### 4.3.1 为什么必须做服务端分页

仅做「前端切片渲染」只能减少 DOM 节点，**无法减少首屏传输与内存占用**——整篇正文仍会一次性下载并常驻内存，与用户明确提出的目标（「减少初始加载时间与内存占用」）不符。因此本期采用**服务端分页 + 前端增量追加**为主机制。

#### 4.3.2 后端设计（拟新增，待确认项 1）

| 端点 | 语义 | 返回 |
|---|---|---|
| `GET /documents/:id/outline` | 轻量大纲，用于目录与深链定位 | `{ documentId, title, pageCount, totalSections, sections: [{ sectionId, heading, order, locator }] }`（**不含 `text`**） |
| `GET /documents/:id/sections?cursor=<order>&limit=<n>` | 按需取正文分页 | `{ items: [{ sectionId, heading, text, order, locator }], nextCursor: number \| null, total }` |

设计要点：

- **游标用 `order` 而非数组下标**：`order` 由解析器写入且稳定，避免后续重排/删除导致错位。
- **`limit` 约束** 1..50、默认 10（DTO 校验，与既有 `QueryDocumentDto` 风格一致）。
- **Mongo 投影**：大纲查询用 projection 只取 `sections.sectionId/heading/order/locator`；分页查询用 `$slice` 取正文片段，避免整篇加载进后端内存。
- **不改动 `GET /documents/:id`**：保留其现有全量语义（详情页依赖 `sections` 标题列表），新增接口零破坏（见待确认项 3）。
- **无 `sections` 文档的兜底**：当 `sections` 为空时，提供一个「按固定字符预算切片」的降级分页（服务端按 `contentLength` 切块），使 P8 场景同样受益；同理用于超长单节。
- 权限沿用 `AuthGuard` + `ownerId` 过滤（与 `findOne` 一致），并补 `ownerId` 越权用例。

#### 4.3.3 前端设计

- 查询层：
  - `useDocumentOutline(documentId)` → 大纲（`useQuery`）。
  - `useDocumentSections(documentId, { initialCursor })` → `useInfiniteQuery`，`getNextPageParam: (last) => last.nextCursor ?? undefined`。
- 渲染层：
  - 首屏仅请求大纲 + 第一页正文；`DocumentPreviewPage` 改为按 `pages.flatMap(p => p.items)` 拼接渲染。
  - 触底哨兵：`IntersectionObserver`（`rootMargin: '600px 0px'`，提前预加载）触发 `fetchNextPage`；卸载时 `disconnect`。
  - 支撑状态：`isFetchingNextPage` / `hasNextPage` / `isError`，对应骨架屏 / 「已到底部」/ 局部重试。
- **深链定位策略**（修复 P7）：先用**大纲**（含 `locator`）计算目标 `order` → 以目标页为 `initialCursor` 取该页 → 若目标不在页首，提供**顶部反向哨兵**加载更早内容；定位完成后 `scrollIntoView` 并高亮。
- **Mock 模式**：`appConfig.enableMockApi` 下按页切片 `mockDocument.sections`，保证本地开发路径一致。
- 渲染成本控制（P10）：章节项 `React.memo`；章节容器加 `content-visibility: auto` + `contain-intrinsic-size`（不支持的浏览器自动降级为普通渲染，无副作用）。

### 4.4 响应式

| 断点 | 布局 |
|---|---|
| ≥ 1200px | 左侧 TOC（240px）+ 正文（最大 `72ch` 居中），右侧留白 |
| 1024–1199px | 左侧 TOC（210px）+ 正文（自适应） |
| 768–1023px | 单栏正文 + 浮动「目录」按钮（打开抽屉） |
| < 768px | 全屏阅读：顶部阅读工具条 + 目录抽屉 + 正文（`--mv-reading-measure` 解除上限，占满可用宽） |

配套：触控目标 ≥ 44px；工具条在移动端考虑 `safe-area-inset`。

### 4.5 兼容性与可访问性

| 项 | 说明 |
|---|---|
| `content-visibility` | Chrome 85+ / Safari 18+ / Firefox 125+；不支持时无副作用（仅失去优化） |
| `IntersectionObserver` | 全目标浏览器支持，用于哨兵与 scroll-spy |
| `scroll-behavior: smooth` | 需尊重 `prefers-reduced-motion: reduce`（改为即时跳转） |
| 可访问性 | TOC `nav[aria-label]` + 当前项 `aria-current="location"`；字号/行距按钮 `aria-pressed`；进度条 `role="progressbar"` + `aria-valuenow`；目录抽屉 Esc 关闭与焦点回收；正文标题语义层级（配合 4.1） |
| 路由懒加载 | 预览页与详情页改为 `React.lazy` + `Suspense`（复用 `lazyPage`，修复 P9） |

## 八、风险与回滚

| 风险 | 说明 | 应对 |
|---|---|---|
| 后端分页与既有全量接口语义并存 | 两套读取路径可能产生数据不一致（如 `sections` 数量） | 分页接口与 `findOne` 复用同一数据源与投影字段；补一致性单测 |
| 超长单节（如单页 PDF 数十万字符） | 按 section 分页仍可能单页过大 | A-3 字符预算兜底；前端 `content-visibility` 控制渲染成本 |
| Markdown 渲染引入体积/耗时 | `streamdown` 可能携带较重依赖（如 mermaid 已分包） | 阶段 C-2 先做体积与渲染耗时测量，超阈值则降级为轻量渲染（待确认项 2） |
| 深链定位与分页结合 | 目标章节不在已加载区间时定位失败 | 以大纲 `order` 计算目标页并以该页为 `initialCursor`；提供反向加载 |
| 滚动加载与 sticky 目录互相影响 | 移动端抽屉 + 滚动容器嵌套 | 阶段 E 统一滚动容器；`sticky` 仅用于桌面 TOC |
| 无 sections 文档 | 该类文档绕过分页 | A-3 兜底分页覆盖；补对应测试用例 |

**回滚**：各阶段独立提交；后端接口为**新增**（不改原接口），前端可通过开关回退到 `getDocument` 全量路径；若阶段 C-2 渲染方案不达标，可单独回滚该步骤而不影响 A/B 阶段成果。
