# 用户名密码登录与注册 实现方案

## 1. Context（背景与目标）

当前系统只有一条登录路径：`POST /v1/auth/dev-login`，它不查数据库，直接把调用方传入的 `userId` 签进 JWT，前端登录页也只让用户填「显示名称」。

这带来两个问题：

1. **没有真正的账户体系**。除开发账号外，任何人都无法获得身份。
2. **历史隐患**：`dev-login` 默认 `userId='dev-user'`（非数字），而所有 `owner_id` 列都是 `BIGINT`，一旦用这个身份查业务数据就会报 `invalid input syntax for type bigint: "dev-user"`。

目标（按 `docs/设计稿/pc端/登陆.png`、`docs/设计稿/pc端/注册.png` 还原）：

- 开发账号由**环境变量**配置（`dev / 123456`），绑定现有 `owner_id = 10001`。
- 其余用户走**注册页**创建账号，注册成功后自动登录进入工作台。
- 登录页改为「用户名 + 密码」，并新增注册页；UI 严格对齐设计稿。

## 2. 现状约束（已核实）

| 事实 | 位置 |
| --- | --- |
| 无任何用户表 / User 实体 | `app.module.ts` entities 白名单内无用户实体 |
| 所有 `owner_id` 均为 `BIGINT`，JS 侧用 string 承载 | `document.entity.ts` 的 `bigintTransformer` |
| ID 生成统一用 `nextSnowflakeId()`（返回数字字符串） | `src/common/snowflake-id.ts` |
| 无 bcrypt / argon2 依赖，但有 `class-validator`、`node:crypto` 可用 | `mind_vault_api/package.json` |
| 迁移需**手工加进白名单**才会执行（`migrationsRun: true`） | `app.module.ts` migrations 数组 |
| `ValidationPipe` 开启 `whitelist + forbidNonWhitelisted` | `main.ts` |
| 全局前缀 `v1` | `main.ts` |
| `AuthModule` 被**无条件**导入，但 `standalone` 模式下不注册 TypeORM | `app.module.ts` L35-L57 |
| 小程序依赖 `POST /auth/dev-login`（传 `userId: '10001'`） | `mind_vault_miniapp/services/auth.ts` |

## 3. 已确认的决策

1. **开发账号**：纯环境变量校验、不落库；ID 绑定现有 `owner_id = 10001`。
2. **注册后**：接口直接返回 token，前端写入 session 并跳 `/app/overview`。
3. **密码哈希**：Node 内置 `crypto.scrypt`，零新依赖。
4. **前端**：严格还原设计稿。

## 4. 后端改动（mind_vault_api）

### 4.1 配置与环境变量

`src/config/configuration.ts` 的 `auth` 段新增：

```ts
auth: {
  jwtSecret: env.JWT_SECRET ?? 'mind-vault-development-secret',
  devLoginEnabled: parseBoolean(env.DEV_AUTH_ENABLED, (env.NODE_ENV ?? 'development') !== 'production'),
  devAccount: {
    id: env.DEV_ACCOUNT_ID ?? '10001',        // 必须是数字，对应现有 owner_id
    username: (env.DEV_ACCOUNT_USERNAME ?? 'dev').trim().toLowerCase(),
    password: env.DEV_ACCOUNT_PASSWORD ?? '123456',
    nickname: env.DEV_ACCOUNT_NICKNAME ?? '开发用户',
  },
},
```

`mind_vault_api/.env` 追加（该文件不入版本库）：

```
DEV_ACCOUNT_ID=10001
DEV_ACCOUNT_USERNAME=dev
DEV_ACCOUNT_PASSWORD=123456
```

### 4.2 用户表与迁移

新增实体 `src/auth/entities/user.entity.ts`（表名遵循 `kh_` 前缀约定）：

```ts
@Entity('kh_user')
export class UserEntity {
  @PrimaryColumn({ type: 'bigint', transformer: bigintTransformer })
  id: string;

  @Column({ type: 'varchar', length: 64 })
  username: string;               // 入库前统一 trim + 小写，保证唯一性不区分大小写

  @Column({ name: 'password_hash', type: 'varchar', length: 255 })
  passwordHash: string;

  @Column({ type: 'varchar', length: 64, nullable: true })
  nickname?: string | null;

  @Column({ type: 'smallint', default: 1 })
  status: number;                 // 1 可用 / 0 禁用

  @CreateDateColumn({ name: 'created_at', type: 'timestamp' }) createdAt: Date;
  @UpdateDateColumn({ name: 'updated_at', type: 'timestamp' }) updatedAt: Date;
}
```

新增迁移 `src/migrations/1790812800000-add-user-account.ts`（写法对齐 `1790380800000-add-review-workspace-schema.ts`）：

```sql
CREATE TABLE IF NOT EXISTS kh_user (
  id BIGINT PRIMARY KEY,
  username VARCHAR(64) NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  nickname VARCHAR(64),
  status SMALLINT NOT NULL DEFAULT 1,
  created_at TIMESTAMP NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMP NOT NULL DEFAULT NOW()
);
CREATE UNIQUE INDEX IF NOT EXISTS ux_kh_user_username ON kh_user(username);
```

`down` 中 DROP INDEX + DROP TABLE。

**必须同步注册两处，否则迁移不会执行**（历史约束）：
- `app.module.ts` 的 `entities` 数组 → 加 `UserEntity`
- `app.module.ts` 的 `migrations` 数组 → 加 `AddUserAccount1790812800000`

### 4.3 密码哈希工具

新增 `src/common/password.ts`，用**异步** `scrypt`（避免同步阻塞事件循环，本项目有 event-loop p99 监控）：

- `hashPassword(plain): Promise<string>` → 格式 `scrypt$N$r$p$salt$hash`，salt 用 `randomBytes(16)`。
- `verifyPassword(plain, stored): Promise<boolean>` → 解析格式，用 `timingSafeEqual` 比较；对格式非法/字段缺失**返回 false 而非抛错**。
- 参数：`N=16384, r=8, p=1, keylen=64`。

### 4.4 DTO（`src/auth/dto/`）

`ValidationPipe` 拒绝未声明字段，DTO 必须覆盖前端所有入参：

- `login.dto.ts`：`username`（`@IsString @IsNotEmpty @MaxLength(64)`）、`password`（`@IsString @IsNotEmpty @MaxLength(128)`）。
- `register.dto.ts`：`username`（`@Matches(/^[a-zA-Z0-9_-]{3,64}$/)`）、`password`（`@MinLength(8) @MaxLength(128)`）。**无 nickname 字段**——设计稿注册页只有用户名/密码/确认密码，`nickname` 由后端取 `username`。

校验失败的文案由 `ValidationPipe` 返回 400，前端统一展示。

### 4.5 AuthService（`src/auth/auth.service.ts`）

保持 `devLogin(userId, nickname)` **原样不动**（小程序在用）。

新增：

- `login(dto)`
  1. `username` 归一化（trim + lowercase）。
  2. **开发账号分支**：若 `devLoginEnabled` 且用户名/密码与 `auth.devAccount` 一致 → 直接用 `devAccount.id`（数字 10001）签发 JWT，`nickname = devAccount.nickname`。
  3. **普通账号分支**：按 `username` 查 `kh_user`；查不到、`status !== 1`、或 `verifyPassword` 失败 → 统一抛 `UnauthorizedException('用户名或密码错误')`（不区分「用户不存在」与「密码错误」，避免枚举用户名）。
  4. 签发 JWT：`{ sub: user.id, nickname: user.nickname ?? user.username }`，`expiresIn: '7d'`。
  5. 返回 `{ accessToken, user: { id, nickname } }`。

- `register(dto)`
  1. `username` 归一化。
  2. 命中**保留用户名**（`auth.devAccount.username`，无论 devLoginEnabled 与否都保留）→ `ConflictException('该用户名不可用')`。
  3. 已存在 → `ConflictException('用户名已被注册')`（保存时靠唯一索引兜底，捕获冲突再转同义错误）。
  4. `id = nextSnowflakeId()`、`passwordHash = await hashPassword(password)`、`nickname = username`，落库。
  5. 直接返回与 `login` 相同结构（自动登录）。

- 新增私有 `issueSession(id, nickname)` 供 `login` / `register` 复用，统一 JWT 签发与响应结构。

### 4.6 AuthController（`src/auth/auth.controller.ts`）

- `POST /v1/auth/login` → `authService.login(dto)`
- `POST /v1/auth/register` → `authService.register(dto)`
- `POST /v1/auth/dev-login`、`GET /v1/me` **保持不变**（`/me` 仍从 JWT 取 `{ id, nickname }`）。

### 4.7 AuthModule 与 standalone 兼容（关键，别踩）

`AuthModule` 被 `app.module.ts` 无条件导入，而 `APP_STANDALONE=true` 时 `TypeOrmModule.forRootAsync` 被跳过。若直接加 `TypeOrmModule.forFeature([UserEntity])`，`pnpm start:standalone` 会因找不到 DataSource 启动失败（worker 未设 standalone，不受影响）。

处理方式——镜像 `app.module.ts` 的条件写法：

```ts
const standalone = buildConfiguration(process.env).runtime.standalone;

@Module({
  imports: [
    JwtModule.registerAsync({ /* 不变 */ }),
    ...(standalone ? [] : [TypeOrmModule.forFeature([UserEntity])]),
  ],
  controllers: [AuthController],
  providers: [AuthService, AuthGuard],
  exports: [AuthGuard, JwtModule],
})
```

`AuthService` 的仓储注入改为可选：`@Optional() @InjectRepository(UserEntity) private readonly users?: Repository<UserEntity>`。standalone 下 `users` 为 undefined，此时**开发账号仍能登录**，普通账号/注册返回 503 语义的错误即可。

## 5. 前端改动（mind_vault_web）

### 5.1 API 层（`src/api/auth.ts`）

- 保留 `AuthUser`、`AuthSession`、`getCurrentUser`。
- 移除 `devLogin` / `DevLoginInput` / `DevLoginResponse`（登录页不再使用；小程序走自己的 `services/auth.ts`，不受影响）。
- 新增：
  - `login(input: { username: string; password: string }): Promise<AuthSession>` → `POST /auth/login`

- 延续现有 `appConfig.enableMockApi` 的 mock 分支写法，返回本地假 session。
- 复用 `jsonRequest`（`src/api/client.ts` 自动注入 `Authorization`、`X-Request-ID`、`Content-Type`）。错误由 `ApiRequestError`（`src/lib/errors.ts`）抛出，`message` 直接用于展示。

## 6. 数据与兼容性

- 开发账号登录后 `owner_id = 10001`，直接看到该 owner 已有数据，不再触发 bigint 报错。
- `POST /auth/dev-login` 保留 → 小程序本地开发模式无需改动。
- 迁移已执行后新增 `kh_user` 表；存量数据（`kh_document` 等）不受影响，无需回填。
- `DEV_AUTH_ENABLED=false`（生产）时，开发账号分支失效，但**注册/登录仍可用**。

## 7. 验证步骤

1. `cd mind_vault_api && pnpm build && pnpm lint && pnpm test` 全绿。
2. 起数据库后 `pnpm start:dev`，确认日志执行了 `AddUserAccount1790812800000`，`kh_user` 表存在（`\d kh_user` 应见到 `ux_kh_user_username` 唯一索引）。
3. 接口冒烟：
   - `POST /v1/auth/login {"username":"dev","password":"123456"}` → 200，`user.id === "10001"`。
   - 错误密码 → 401 `用户名或密码错误`。
   - `POST /v1/auth/register {"username":"tester","password":"12345678"}` → 200 且返回 token；重复注册 → 409；密码 7 位 → 400。
   - `POST /v1/auth/login {"username":"tester","password":"12345678"}` → 200，且带该 token 请求 `/v1/me`、`/v1/documents` 正常（owner 为数字，无 bigint 报错）。
   - `POST /v1/auth/dev-login {"userId":"10001"}` 仍 200。
4. `pnpm start:standalone` 能正常起来（验证 4.7 的条件注册）。
5. 前端：`cd mind_vault_web && pnpm typecheck && pnpm lint && pnpm test`，再 `pnpm dev` 后用浏览器核对登录/注册两页与设计稿的还原度、密码「显示」切换、互链跳转、移动端断点折叠。

## 8. 风险与待确认

- **插画保真度**：设计稿左侧是手绘平板线稿。内联 SVG 可先做简化线稿版；若要像素级一致，需要设计侧提供 SVG 源文件。当前方案按「简化线稿 + 后续替换」处理。
- **开发账号密码强度**：`123456` 仅 6 位，低于注册页「至少 8 位」规则。它来自环境变量、不受注册校验约束——这是刻意为之，但需确保 `DEV_AUTH_ENABLED=false` 在非开发环境生效。
- **登出**：设计稿未涉及，本次不改；现有 `useAuthStore.clear` 已可用。
- **限流**：登录/注册无频率限制（现有进程内限流不适用于多副本），本次不做，如需可在后续接入共享存储限流。
