## 一、背景与目标

### 1.1 背景

Web 端左侧导航（桌面）与底部导航（移动端）已经预留「个人设置 / 我的」入口，指向 `/app/settings/account`（[navigation.ts#L9](file:///Users/susucain/开发/mind-vault/mind_vault_web/src/app/navigation.ts#L9)、[AppShell.tsx#L51-L70](file:///Users/susucain/开发/mind-vault/mind_vault_web/src/app/AppShell.tsx#L51-L70)），但该路由实际渲染的是一个通用占位组件：

```tsx
{ path: 'settings/*', element: <PlaceholderPage title="Settings" /> },   // router.tsx:91
```

`PlaceholderPage` 只输出 `page-section` + `StatusBadge("Coming soon")` + `EmptyState`（[pages.tsx#L17-L30](file:///Users/susucain/开发/mind-vault/mind_vault_web/src/app/pages.tsx#L17-L30)）。也就是说：**设置页是一个「点了能进、进去什么都没有」的空壳**，而用户指令中要求的五类功能中，除「查看个人信息」有极少量痕迹外，其余四项前后端均不存在。

小程序端已有一套完整的「我的 + 记忆管理」实现（[profile.wxml](file:///Users/susucain/开发/mind-vault/mind_vault_miniapp/pages/profile/profile.wxml)、[memory.wxml](file:///Users/susucain/开发/mind-vault/mind_vault_miniapp/pages/memory/memory.wxml)），Web 端可借鉴其**信息结构与小屏文案**，但需按桌面阅读场景重新设计交互。

### 1.2 目标

按用户指令的四个维度对 Web 端设置页做系统性建设：

1. **功能完整性**：长期记忆管理（查看/分类/搜索/增删改）、退出登录、个人信息查看、更换用户名、更换头像，五项全部可用。
2. **UI 设计**：复用既有暖纸书房设计系统，建立清晰的信息层级与分区导航，桌面 / 平板 / 移动三档均可用。
3. **交互体验**：表单即时校验与明确错误提示、危险操作二次确认、加载与操作反馈、必要过渡动效。
4. **工程质量**：类型安全、边界完备（开发账号 / 存储未启用 / 记忆满仓 / 空态）、单元测试覆盖、不引入无谓依赖。

### 1.3 非目标（本期不做）

| 项 | 原因 |
|---|---|
| 后端 JWT 吊销 / 会话黑名单 | 已确认采用「前端清理为主」；引入黑名单需新增 Redis 或吊销表，与本次收益不匹配（风险见 9.2） |
| 修改密码 | 用户指令未包含；且当前后端无任何改密接口，属独立安全流程，另行评估 |
| 账号注销 / 数据导出 | 风险高、合规口径多，不在本次范围 |
| 主题 / 语言 / 通知等偏好设置 | 目前无对应后端能力，避免了「放一堆假开关」 |
| 小程序端改造 | 用户明确限定 Web 端；小程序已具备记忆管理页 |
| 邮箱 / 手机号绑定 | 当前用户模型无这两个字段 |

## 四、设计目标与原则

| 原则 | 具体约束 |
|---|---|
| **复用优先** | 不引入任何新依赖（无裁剪库、无表单库、无头像组件库）；样式全部复用既有 token 与组件类，新增类统一 `settings-` 前缀 |
| **向后兼容** | 后端所有改动不得破坏小程序现有调用（小程序调 `/memories?status=ACTIVE` 拿 `{items}`、调 `/auth/dev-login`）。分页只在显式传参时生效，见 6.3 |
| **边界完备** | 开发账号不落库、对象存储未启用、记忆满仓、空态/错态/加载态，每一种都要有明确表现，不能出现白屏或静默失败 |
| **安全前置** | 改用户名需验证当前密码；危险操作二次确认；退出登录清理 token + 缓存 + 偏好；错误提示不泄漏内部信息 |
| **可测试** | 校验规则、标签映射、退出清理逻辑等纯函数独立成文件，前后端各补单元测试 |
| **渐进交付** | 按第五章阶段推进，每阶段可独立验证、独立提交，不存在「必须一次做完才能跑」的中间态 |

  avatarKey: string | null;  // 有则前端可请求 /me/avatar（新增）

**昵称约束**：长度上限 **32 字符**（DTO `@MaxLength(32)`），入库前 `trim`，不允许为空（不带「清空昵称」操作，避免出现无展示名的用户）。`kh_user.nickname` 列宽 64 足够容纳。

**关键边界——开发账号不落库**：`dev` 账号（默认 id `10001`）来自环境变量、不在 `kh_user` 中（[auth.service.ts#L116-L124](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/auth/auth.service.ts#L116-L124)）。因此 `getProfile` 逻辑为：

1. 查库 `findOne({ where: { id } })`；
2. 命中 → 返回真实资料；
3. 未命中且 `id === devAccount().id` → 返回合成资料：`username = dev.username`、`nickname = dev.nickname`、`avatarKey = null`、`createdAt = null`、`isDevAccount = true`；
4. 未命中且非开发账号 → `NotFoundException`（防止令牌泄露 ID 探测）。

**写操作的开发账号策略**：改用户名、改头像、改昵称对开发账号一律 `ForbiddenException('开发账号不支持修改资料')`。这与「dev 账号不落库、改不了」的事实一致，避免出现「改完刷新就回滚」的幽灵行为。前端据 `isDevAccount` 提前禁用入口并给出说明，而不是等报错。

#### 5.1.3 改用户名（`PATCH /me/username`）

必须实现用户要求的「输入验证 + 重复检查 + 修改确认」三重机制：

1. **输入验证**：DTO 复用 `USERNAME_PATTERN = /^[a-zA-Z0-9_-]{3,64}$/`（[register.dto.ts#L3](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/auth/dto/register.dto.ts#L3)）；`currentPassword` 走 `@IsString() @MinLength(1)`。
2. **修改确认**：服务端用 `verifyPassword(currentPassword, user.passwordHash)` 校验，失败抛 `UnauthorizedException('当前密码不正确')`。**这是「确认机制」的服务端落点**——前端弹窗里的密码输入不是摆设。
3. **重复检查**：
   - 归一化 `username.trim().toLowerCase()`；
   - 与开发账号登录名同名 → `ConflictException('该用户名不可用')`（对齐注册逻辑）；
   - 与自身当前 `username` 相同 → 直接返回当前 profile（幂等，不报错、不重复写）；
   - 与其他用户重名 → `ConflictException('用户名已被占用')`；
   - `save` 时唯一索引冲突兜底 `catch` → 同上 409（并发场景）。
4. **昵称联动**：若 `nickname` 恰好等于**旧** username（即用户从未自定义过昵称，保持注册时的默认一致语义），则同步把 `nickname` 更新为新 username；否则保留用户自定义昵称不动。
5. 成功后重新签发 token 并返回，前端 `setSession` 落盘。

> 改 `username` 不影响 JWT 有效性（载荷里只有 `sub` 与 `nickname`），但为保持前端展示一致，统一重新签发。

### 5.5 前端：头像上传 / 预览 / 裁剪（阶段 E）

#### 5.5.1 交互流程

```
点击「更换头像」
 → <input type="file" accept="image/png,image/jpeg,image/webp" hidden>
 → 选择文件
 → 客户端预校验（类型白名单、≤5MB）→ 不通过：就地错误提示，不打开裁剪
 → 读取图片 → 打开 AvatarCropDialog（方形 1:1 视口，可拖动 + 缩放，支持重置）
 → 确认 → canvas 输出 512×512 WebP（quality 0.9）→ Blob
 → 乐观预览（立刻显示本地 object URL）→ POST /me/avatar
 → 成功：写入新 profile、释放旧 URL、Toast「头像已更新」
   失败：回滚为原头像、展示服务端错误文案（含 503「存储未启用」与类型/大小拒绝）
```

#### 5.5.2 裁剪实现（不引第三方库）

`AvatarCropDialog.tsx` 用原生 `canvas`：

1. `createImageBitmap(file)` 解码；
2. `<canvas>` 尺寸固定为 CSS 320×320，视口为正方形；维护 `scale`（1–3）与 `offsetX/offsetY` 状态；
3. 拖动：`pointerdown/pointermove/pointerup`（Pointer Events 统一鼠标与触摸，桌面/移动同一套代码）；
4. 缩放：`input[type=range]` 滑杆（比双指手势更省事且可访问）；
5. 输出：另建 512×512 离屏 canvas，按视口映射绘制可见区域，`canvas.toBlob(cb, 'image/webp', 0.9)`；浏览器不支持 WebP 编码时回落 `'image/jpeg'`（用 `toBlob` 返回 `null` 做特性探测）；
6. `offset` 边界钳制（不让图片被拖出视口留下空白）；
7. 键盘可访问：方向键微调偏移，`Esc` 关闭，`Enter` 确认。

> 选原生 canvas 而非 `react-easy-crop`：需求只有「方形裁剪 + 拖动 + 缩放」，自实现约 120 行且零依赖；引入库会为这点功能增加维护面与体积。

#### 5.5.3 默认头像（无头像时）

`AvatarUploader` 在无 `avatarKey` 时渲染首字母圆形底色头像：取 `nickname` 首字符（中文取首字，英文大写），底色从 `--mv-primary` 派生的固定色板中按 `id` 取模选取（同一用户始终同色，不用随机）。**不生成图片资源、不请求占位图**。
