## 一、方案背景

### 1.1 现状

平台已经具备一套完整的三路检索能力，但它目前**只作为问答（RAG）的内部环节存在**，用户无法直接使用：

- 后端已有独立检索控制器 [retrieval.controller.ts](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/retrieval/retrieval.controller.ts)，暴露 `POST /v1/retrieval/keyword|vector|graph|hybrid` 四个接口，但**没有任何前端页面调用它们**。
- 前端 [router.tsx](file:///Users/susucain/开发/mind-vault/mind_vault_web/src/app/router.tsx) 的 `/app` 下没有检索路由；全仓不存在检索页、检索 API 模块或 Chunk 相关类型。
- 三路检索的实际承载：
  - **关键字检索** —— Elasticsearch `multi_match`（`titlePath^3` + `text`），中文 `ik` 分词，标题精确命中加权（[elasticsearch-index.service.ts](file:///Users/susucain/开发/mind-vault/mind_vault_api/src/retrieval/es/elasticsearch-index.service.ts)）。
  - **语义检索** —— Elasticsearch `dense_vector` kNN（cosine，1024 维），**不是 pgvector**（pgvector 仅服务长期记忆表）。
  - **图谱检索** —— Neo4j Cypher 实体邻域展开，再经 `sourceChunkId` 回捞 ES 中的 Chunk 正文。

### 1.2 问题

| 编号 | 问题 | 影响 |
|---|---|---|
| P1 | 检索能力只能通过"提问"间接使用，无法指定检索方式、无法限定资料集、无法看原始片段 | 用户无法做定向查证，问答给出的结论难以溯源 |
| P2 | 无关键词高亮，无相关性评分展示，无结果统计 | 命中原因不透明，用户需要自行在长文档里二次寻找 |
| P3 | 图谱数据已抽取入库（实体/关系），但除问答外无任何可视化出口 | 已投入的图谱抽取成本（`graph.extract` worker）无法转化为用户价值 |
| P4 | 无检索历史 | 重复检索需重新输入与配置 |

### 1.3 机会

后端三路检索接口与数据结构**已经就绪**，图谱抽取链路**已经在跑**。本期工作主要在"接口补齐 + 前端呈现"，属于**低成本高杠杆**的增量建设，且能与问答模块共享同一套检索口径，避免两套逻辑分叉。

## 二、方案目标

### 2.1 业务目标

1. 提供独立的检索入口，支持关键字 / 语义 / 图谱三种方式**显式切换**并保留用户输入。
2. 让检索结果**可读、可溯源、可评估**：高亮命中片段、展示相关性评分、显示定位信息、可跳转原文。
3. 把已入库的图谱数据**可视化**：实体—关系网络支持缩放、平移、展开/折叠、按类型过滤、点击查看详情。

### 2.2 技术目标

1. **复用而非重写**：统一检索接口在 `RetrievalService` 之上做编排，不复制三路检索逻辑。
2. **零破坏**：现有 `/v1/retrieval/*`、`/v1/graph/search` 与问答链路的行为与响应结构保持不变。
3. **可测试**：新增服务层方法均配套 Jest 单测，前端配套 Vitest 测试，沿用仓库既有测试惯例。
4. **可控性能**：中等规模图谱（≤ 300 节点 / ≤ 600 边）在桌面端交互流畅，不阻塞主线程。
5. **历史服务端化**：检索历史按 `ownerId` 落库，跨用户严格隔离；刷新页面或更换设备后可恢复，不依赖浏览器本地存储。

### 2.3 非目标（本期不做）

| 项 | 原因 |
|---|---|
| 检索结果导出（CSV / Markdown） | 非本次核心诉求，避免范围膨胀 |
| 检索历史跨用户共享 / 团队协作视图 | 历史在服务端**按 `ownerId` 严格隔离**，仅本人可见；不做共享历史、团队视图与跨账号聚合 |
| 图谱编辑（增删实体/关系） | 图谱为抽取派生数据，本期只读 |
| 移动端小程序检索页 | 本期仅 Web 端；小程序端另行评估 |
| 跨资料集的语义去重 / 重排序（rerank）模型 | 属检索质量优化，与页面建设解耦 |

### 2.4 验收标准

- 三种检索方式均可独立发起并返回结果，切换方式时**输入内容不丢失**。
- 关键字检索结果中命中词以高亮呈现；结果卡片展示评分、来源方式、文档标题与定位。
- 图谱面板可缩放/平移，点击节点可展开邻域并查看详情，支持按实体类型与关系类型过滤。
- 检索历史在服务端按用户留存（仅本人可见），刷新或换设备后仍可一键回填并重新检索；可删除单条与清空全部。
- 桌面端（≥ 1100px）与移动端（< 768px）布局均可用。
- `pnpm lint` / `pnpm build` / `pnpm test`（web）与 `npm run build` / `npx jest`（api）全部通过。

### 4.3 功能区设计

#### 4.3.1 检索功能区

| 方式 | 输入语义 | 交互要点 |
|---|---|---|
| 关键字 | 词/短语 | 支持 `""` 精确短语（转义后传给 ES `match_phrase`）、普通模糊；命中词高亮 |
| 语义 | 自然语言问题 | 提示"用一句话描述你想找的内容"；展示相似度评分（0~1） |
| 图谱 | **实体名称** | 输入框下方展示实体联想下拉；留空时展示「热门实体」以供点击 |

- 精确匹配与模糊搜索的切换**不新增 UI 开关**，而是由用户输入决定：输入被双引号包裹 → 走 `match_phrase` 精确短语；否则走 `multi_match` 模糊。此规则在输入框下方以 hint 文案说明，避免增加控件密度。
- 关键词高亮由后端返回**分段结构**而非 HTML 字符串，前端直接渲染 React 节点，**不使用 `dangerouslySetInnerHTML`**（详见 4.7.4）。

#### 4.3.2 检索控制区

- **类型切换**：`Tabs` 组件，三态互斥；切换时保留 `query`、`datasetIds`、高级选项与图谱焦点，仅重置分页。
- **高级选项**（默认收起，展开为一行）：
  - 时间范围：`近 7 天 / 近 30 天 / 近 1 年 / 不限`（映射为 ES `range` on `updatedAt`）。
  - 结果数量（每页）：`10 / 20`（受后端上限约束）。
  - 相关性排序：`相关度优先 / 最新优先`。
  - 图谱专属：跳数 `1 / 2 / 3`。
- **检索历史**：`Popover` + 列表，点击条目回填全部查询条件并立即检索。
  - **存储位置：服务端**（表 `kh_search_history`），**按 `ownerId` 隔离，不同用户互不可见**；前端不使用 localStorage。
  - **写入方式：后端自动记录**，前端不发写请求 —— `POST /v1/retrieval/search` 编排完成后由后端调用 `SearchHistoryService.record()`，仅在 `page === 1` 时记录，翻页不产生重复条目。
  - **去重与保留**：按 `(ownerId, mode + query + datasetIds + entityNames + filters)` 计算 `dedupeKey` 做唯一约束，命中已有记录则刷新 `resultCount` 与 `createdAt` 而不新增行；每用户仅保留最近 **50** 条，写入时顺带裁剪超出部分。
  - **记录内容**：`mode / query / datasetIds / entityNames / filters(sort,from,to,pageSize,maxHops) / resultCount / createdAt`；**不存储结果正文**（体积与隐私考虑）。
  - 前端在检索成功（`page === 1`）后 `invalidateQueries(['search-history'])`，使历史列表即时反映最新记录。
  - 提供「删除单条」与「清空历史」。

#### 4.3.3 结果展示区

统一结果卡片模板，按来源方式差异化标记：

```
┌──────────────────────────────────────────────────────────────┐
│ 相关度 ▓▓▓▓░ 0.92        产品架构说明  ·  第 3 页 · 第 12–18 行 │
├──────────────────────────────────────────────────────────────┤
│ …… 这里讲的是「向量检索」的召回策略，与 **关键字检索** 互为补充 …… │
├──────────────────────────────────────────────────────────────┤
│ [关键字] [语义]                              [查看原文 ↗]      │
└──────────────────────────────────────────────────────────────┘
```

- **标题行**：相关性评分（条形 + 数值）、文档标题、定位 chip（复用 `DocumentLocatorView`）、资料集名称（次级）。
- **正文行**：命中片段；高亮词用主色底/加粗，不使用刺眼色；片段长度由后端控制（约 240 字符，命中词居中）。
- **底部行**：来源标记（`关键字 / 语义 / 图谱`，混合命中显示多个）、跳转原文（跳 `/app/library/documents/:documentId/preview?<locator>`）。
- **评分口径差异必须在 UI 上消除歧义**：由于三路 score 量纲不同，前端按 `mode` 决定展示方式 —— 关键字展示归一化后的相对分（后端给出 0~1 归一值），语义展示 kNN 相似度，图谱展示"命中关系数/跳数"而非分数（图谱本无评分）。混合模式展示 RRF 融合分并标注「融合排序」。

#### 4.3.4 图谱可视化区

- **画布能力**：缩放、平移、适应视图（fitView）、框选、节点拖拽（节点数 > 150 时默认关闭拖拽以保帧率）。
- **节点**：按实体类型着色（类型映射到主题色板，见 4.5.3）；显示实体名，`degree`（关联数）以节点半径或角标体现。
- **交互**：
  - 单击节点 → 右侧/底部「节点详情」出现（实体名、类型、关联数、关系列表）。
  - 双击节点或点「以此为焦点展开」→ 调用 `neighborhood` 拉取 1 跳邻域并合并进画布（展开）。
  - `Shift + 单击` 或详情面板「收起」→ 折叠该节点的叶子邻域（折叠）。
- **过滤**：`Popover` 面板，按实体类型（PERSON / PROJECT / TECHNOLOGY / CONCEPT / ORGANIZATION / EVENT）与关系类型（USES / USED_FOR / DEPENDS_ON / CAUSES / RELATED_TO / PART_OF / CREATED_BY / MENTIONED_WITH）多选过滤；过滤在前端进行，不重新请求。
- **性能策略**：
  - 节点上限 300、边上限 600；超出时提示「图谱较大，已截断，请用过滤缩小范围」。
  - 力导向布局在 **Web Worker** 中计算，主线程只负责渲染。
  - 节点数 > 150 时启用 `onlyRenderVisibleElements` 与简化节点组件（去掉次级文案）。
  - 布局迭代收敛后停止（`alpha` 衰减至阈值即 `simulation.stop()`），不做持续动画。

#### 4.4.2 状态保留策略

| 状态 | 存放位置 | 理由 |
|---|---|---|
| `mode / query / datasetIds / sort / from / to / pageSize / entity / hops` | **URL 查询参数**（`useSearchParams`） | 刷新、前进后退、分享链接均可还原 |
| 输入框草稿（未提交文本） | 组件局部 state + 300ms 防抖后写 URL | 打字不产生历史记录与请求风暴 |
| 图谱焦点节点、已展开节点集合、类型过滤 | 组件 state + `sessionStorage` 恢复 | 图谱属会话内探索状态，不适合进 URL |
| 检索历史 | **服务端**（`kh_search_history`，按 `ownerId` 隔离） | 跨设备可恢复、跨用户不共享；前端只做 Query 缓存与失效，不用 localStorage |

> 关键点：`mode` 与 `query` 同存于 URL，因此**切换检索方式时输入天然保留**，无需额外状态同步逻辑。

#### 4.6.5 图谱可视化选型

| 候选 | 优势 | 劣势 | 结论 |
|---|---|---|---|

#### 4.7.3 检索历史接口

> 检索历史为**服务端存储**，按 `ownerId` 隔离，**不同用户不共享**；前端不使用 localStorage，也不发写请求。

**数据表** `kh_search_history`

```sql
CREATE TABLE IF NOT EXISTS kh_search_history (
  id                VARCHAR PRIMARY KEY,
  owner_id          BIGINT       NOT NULL,
  mode              VARCHAR(16)  NOT NULL,
  query             VARCHAR(200) NOT NULL,
  dataset_ids_json  JSONB        NOT NULL DEFAULT '[]',
  entity_names_json JSONB        NOT NULL DEFAULT '[]',
  filters_json      JSONB        NOT NULL DEFAULT '{}',
  result_count      INT          NOT NULL DEFAULT 0,
  dedupe_key        VARCHAR(64)  NOT NULL,
  created_at        TIMESTAMP    NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS ix_kh_search_history_owner_created
  ON kh_search_history(owner_id, created_at DESC);

-- jsonb 没有默认 btree 操作符类，无法直接参与唯一约束，
-- 故用服务端计算的 dedupe_key 承担「同条件只留一条」的去重
CREATE UNIQUE INDEX IF NOT EXISTS ux_kh_search_history_owner_dedupe
  ON kh_search_history(owner_id, dedupe_key);
```

`dedupeKey = sha256(mode | query | datasetIds(排序后) | entityNames(排序后) | filters(固定键序))` 取前 32 位十六进制，由服务端计算，前端不感知。

**写入时机（由后端自动完成）**

- `POST /v1/retrieval/search` 编排完成后调用 `SearchHistoryService.record()`；**仅 `page === 1` 记录**，翻页不重复。
- 写入用 `INSERT ... ON CONFLICT (owner_id, dedupe_key) DO UPDATE SET result_count = EXCLUDED.result_count, created_at = NOW()`，命中已有记录只刷新而不新增行。
- 单用户记录数超过 **50** 条时，顺带删除最旧的超出部分，避免表无限增长。
- 写库异常由 `try/catch` 隔离，仅记 warn 日志，**不影响检索响应**。

**列表** —— `GET /v1/search-history?limit=20`

```jsonc
{
  "items": [
    {
      "id": "1856392847563010048",
      "mode": "keyword",
      "query": "向量检索的召回策略",
      "datasetIds": ["1234567890"],
      "entityNames": [],
      "filters": { "sort": "relevance", "from": null, "to": null, "pageSize": 10, "maxHops": 1 },
      "resultCount": 128,
      "createdAt": "2026-10-05T02:31:07.000Z"
    }
  ]
}
```

- `limit`：可选，1..50，默认 20；按 `createdAt DESC` 排序。
- 只返回当前 `ownerId` 的记录。

**删除单条** —— `DELETE /v1/search-history/:id`

- 在 `ownerId` 匹配的前提下删除；非本人记录返回 `NotFoundException`（沿用复习模块既有约定，不泄露记录是否存在）。

**清空** —— `DELETE /v1/search-history`

- 删除当前用户全部记录，返回 `{ "deleted": 12 }`。

约定：

- 三个端点均受 `AuthGuard + RateLimitGuard` 保护；`ownerId` 一律取自 `@CurrentUser()`，**请求体与查询参数都不接受该字段**。
- `filters` 为嵌套对象，DTO 需用 `@ValidateNested()` + `@Type(() => SearchHistoryFiltersDto)` 显式声明，否则全局 `forbidNonWhitelisted` 会直接拒绝该字段。

#### 4.7.4 高亮的安全约定

- ES `highlight` 使用自定义 `pre_tags: ["\u0002"]`、`post_tags: ["\u0003"]`（不可见控制字符），`fragment_size ≈ 240`、`number_of_fragments: 1`。
- 服务端把命中片段按这两个标记切分为 `HighlightSegment[]`，**不返回 HTML**。
- 前端 `HighlightText` 组件按分段渲染 `<span>`，**不经过 `dangerouslySetInnerHTML`**，从根本上规避 XSS。
- 对 `ik` 分词产生的碎片化高亮做最小合并（相邻同命中段合并），避免"逐字高亮"的观感问题。

#### 4.7.5 评分口径与分页约束（重要）

三路 score 量纲不同，必须在协议层显式标注，UI 才能正确表达：

| mode | `scoreKind` | 说明 | 展示方式 |
|---|---|---|---|
| keyword | `normalized_bm25` | ES BM25 分经 min-max 归一化到 0~1 | 相关度条 + 数值 |
| vector | `cosine_similarity` | ES kNN 返回 `(1+cos)/2`，天然 0~1 | 相似度条 + 数值 |
| graph | `graph_degree` | 图谱路径**没有相关性分数**，用"命中关系数 / 跳数"代替 | 显示"关联 N 条"，不显示评分条 |
| hybrid | `rrf_fusion` | RRF 融合分（排名分，非相似度） | 显示"融合排序"标签 + 相对条 |

分页约束（必须写进实现说明，避免"深翻页返回空"的误解）：

- **keyword / hybrid**：ES `from + size` 支持正常翻页。
- **vector**：kNN 的 `k` 即返回上限，翻到第 N 页需 `k ≥ page × pageSize`，因此 `k` 上限设为 100，**最多支持约 5 页 × 20 条**；超出时 `hasNext = false` 并返回 `truncated: true` 提示。
- **graph**：先按 `sourceChunkId` 去重回捞，再本地分页，`total` 为回捞后总数。

## 八、风险评估

| 编号 | 风险 | 影响 | 概率 | 应对措施 |
|---|---|---|---|---|
| R1 | `@xyflow/react` 在 200+ 节点自定义节点下帧率不达标 | 图谱体验下降，需切换备选库 | 中 | 阶段 0 spike 前置验证；不达标即切换 `react-force-graph`，但需重估主题定制成本 |
| R2 | ES `highlight` 与 `ik` 分词导致高亮碎片化（逐字高亮） | 观感差 | 高 | 服务端做相邻段合并与最小长度阈值；必要时改用 `unified` highlighter |
| R3 | 语义检索深翻页受 kNN `k` 上限约束 | 用户以为有更多结果却加载不出 | 高 | 协议显式返回 `hasNext=false` + `truncated=true`，UI 明确提示"已到可翻页上限"；文档写明约束 |
| R4 | 三路评分量纲不同造成误读 | 用户误判结果质量 | 中 | `scoreKind` 显式标注；图谱不显示评分而显示关联数；混合模式标注"融合排序" |
| R5 | 关键字路径新增 `highlight`/分页/排序改动波及问答链路 | 问答检索回归 | 中 | 新增参数均为可选且默认值与现状等价；阶段 1 强制做既有端点回归验证 |
| R6 | 前端筛选（资料集/时间/排序）引发请求风暴 | 触发 60 次/分钟的限流（429） | 中 | 输入 300ms 防抖 + 条件变更即取消上一请求（AbortController，`client.ts` 已具备中断能力）；必要时在阶段 4 将限流计数改为共享存储 |
| R7 | 图谱截断（300 节点上限）让用户误以为数据缺失 | 认知偏差 | 中 | 显式"已截断"提示 + 引导使用类型过滤/缩短跳数 |
| R8 | 全局 `forbidNonWhitelisted` 导致前端多传字段即 400 | 联调受阻 | 中 | 阶段 0 冻结 DTO 字段清单；前端请求体严格按契约构造，禁止透传原始 state |
| R9 | 图谱数据本身不完整（抽取质量/删除残留） | 可视化出现孤点或跨文档噪声 | 中 | 复用既有约定按 `sourceChunkId` 过滤；UI 增加"仅显示与当前资料集相关"开关作为兜底 |
| R10 | 扩大范围（导出、rerank、团队共享历史） | 延期、质量下降 | 中 | 已在 2.3 明确列为非目标；任何范围变更需走第九章变更管理 |
| R11 | 每次检索都写库造成写入放大、历史表无限增长 | 表膨胀、写压力上升 | 中 | 仅 `page === 1` 记录；`(owner_id, dedupe_key)` 唯一索引 + `ON CONFLICT DO UPDATE` 去重；每用户仅保留最近 50 条并在写入时裁剪 |
| R12 | 历史写库失败，或迁移未注册导致功能静默失效 | 历史为空且无任何提示 | 中 | 写库用 `try/catch` 隔离、失败仅记 warn 不影响检索；迁移必须注册进 `app.module.ts` 白名单（既有硬约束），阶段 1 显式验证表已创建 |
